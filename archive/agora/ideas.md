## 하려다 만 것 — v4.1 라운드 잔여 (CR-001)
- **디자인 이미지 토큰 교체 1패스**: 최종 브랜드 색·타이포 이미지가 오면 `:root` 토큰값만 갈아끼워 전 화면 일괄 스킨. (골격은 v4.1 라운드에서 확정, 비주얼만 대기)
- **캘린더 그리드 v4.1 정합**: 주간(7일×세로 시간축)·월간(다일 관통 막대)을 프로토타입대로 재작성(일간은 완료). 위치 계산·겹침 스택 처리가 큰 단위.
- **첨부 EXIF 제거**: 현재 익명 게시판은 첨부 비허용이라 미해당 — 향후 익명첨부 허용 시 활성화.

## 떠오른 스파크 (다른 프로젝트로 분화 가능)
- **CR(변경요청) 인테이크 레일**: 기획 원본을 `resource/changes/` 에 떨구면 → 영향분석(REQ-ID·화면·컴포넌트·토큰·DB·API·테스트) → `docs/changes/CR-NNN-*.md` 정본화 → 격리 브랜치 작업 → 검증 → 머지로 흐르는 멱등 워크플로우. **원본=resource/ · 정본=docs/** 분리와 신구 REQ-ID 매핑표(크로스워크)가 핵심. 이건 second-brain 레일의 "운영 중 프로젝트에 새 요구가 들어올 때" 모듈로 일반화할 수 있다(현재 레일은 신규 창작→개발→배포만 다룸 — **변경 인테이크 게이트는 미설계**).
- **자립형 핸드오프 브리프 합성기**: 한 프로젝트의 흩어진 문서(상호참조·신규맥락 섞임)를 "다른 LLM에 그대로 붙여넣을" **단일 자기완결 .md**로 합성(맥락·내부 ID·링크 제거, 구조·인증·동작·리스크만). 목적(이해/감사 vs 재구축)에 따라 깊이 조절. → 아카이브 distill의 "외부 공유용 export" 변형으로 재사용 가능.
- **"DB가 진실을 강제한다" 패턴 라이브러리**: 예약·자원 선점 도메인이면 어디든 `tstzrange` + `EXCLUDE USING gist`로 겹침을 앱 로직이 아니라 제약으로 차단 → 동시성 레이스 무료 제거. 캘린더형 SaaS 공통 코어로 재사용 가능.
- **메타데이터 기반 동적 게시판 엔진**: 단일 posts 테이블 + `author_shape` CHECK로 익명/실명 겸용, 관리자가 코드 수정 없이 보드 생성. "스키마는 표현이 아니라 정책을 강제한다"는 발상은 폼 빌더·동적 설문 등으로 일반화 가능.
- **심층 방어 익명성 모듈**: 핸들러(신원 미독취)·저장(컬럼 부재)·로깅(프록시+앱+에러+감사 침묵)을 한 묶음으로 제공하는 재사용 자산 — 제보/신고 시스템의 공통 부품.
- **무중단 롤링 + graceful shutdown 보일러플레이트**: probe 분리·preStop 드레인·RWX 첨부 공유·SIGTERM 풀 정리를 한 매니페스트 템플릿으로(= second-brain `intranet` 프로파일의 시드).
- **Design-ready 스킨 흡수 키트**: 디자인 토큰 단일출처(`:root`) + 데이터색 분리 + `[data-theme]` 오버라이드 레이어 + "이미지→토큰명" 매핑시트를 한 묶음 자산으로. "구조 먼저 확정, 최종 비주얼은 이미지 도착 시 토큰 1패스로 흡수" 핸드오프(기획↔디자인 분리)를 표준화 — 디자인이 늦게 확정되는 모든 프로젝트의 공통 부품.
- **대규모 리디자인 리스크관리 워크플로우("샘플 1개→승인→확장")**: 화면이 여러 개(수십 개)일 때 전체를 한 번에 잘못된 방향으로 만드는 낭비를 피하려 셸+대표 화면 1개만 먼저 재구축해 승인받은 뒤 나머지를 순차 진행하는 패턴을 agora CR-001에서 실제 사용했다. `/develop`/`/creative` 레일에 "화면 수 N개 이상이면 샘플 승인 게이트를 자동 삽입" 규칙으로 일반화할 수 있다.
- **자원예약 도메인 체크리스트: "신청자"≠"실제 사용자"**: 예약형 자원(차량·회의실·장비 등) 도메인에서 신청한 사람과 실제로 쓰는 사람이 다를 수 있다는 걸 반복해서 놓쳤다(agora 차량예약: 운전자≠신청자). 예약/자원배정 도메인 스펙 작성 시 이 필드 분리 여부를 기본 질문으로 넣는 체크리스트 항목으로 승격 가능.
- **CI 변수 vs k8s Secret 삭제 판정 체크리스트**: "이미 배포됐으니 CI 변수는 지워도 되나" 질문에 쓴 판단 축(빌드용/클러스터접근용/시크릿백업용 분류 · Masked 형식요건 · Protected는 체크해제 대신 브랜치를 보호 등록)을 `deploy-runbook` 스킬의 배포 후 운영 정리 체크리스트로 일반화할 수 있다.

## 개선 아이디어 (이 프로젝트를 다시 한다면)
- **운영 안전망을 처음부터**: CI 테스트 게이트·`/api/health`·전역 Error Boundary·graceful shutdown을 스캐폴드 1일차에 깔면 이후 리팩토링 회귀를 자동 탐지(이번엔 개선 라운드에서 뒤늦게 추가).
- **구조적 중복 선제 추출**: 관리자 마스터 화면·예약 폼·캘린더 칩이 거의 동일했음 → `GenericMasterClient`/`useReservationForm`/`EventChip`을 초기부터 두면 ~400줄 절감.
- **시크릿/배포 자동화 경로를 초반에 합의**: 러너 권한 제약(이미지 교체만)을 모른 채 "CI가 전부 생성" 가정 → 막힘. 권한 모델을 먼저 확인하고 좁은 patch Role을 설계.
- **마이그레이션 추적 테이블·역방향 전략**을 0번 마이그레이션부터 도입(번호체계가 느슨해 운영 반영이 수동·위험).
- **새 프로토타입 적용 시 골격부터 가시화**: 요구 델타(백엔드·데이터)에 먼저 손대면 화면이 기존과 똑같아 보여 "새로 할까" 회의를 부른다. 셸·IA·내비 골격을 프로토타입에 맞춰 **먼저** 렌더하고 방향 확인을 받은 뒤 기능 델타로 들어갈 것. (요구가 "변경"인지 "신규"인지도 가정 말고 코드 grep으로 확인 — 이번엔 주행거리 보정을 기구현으로 오인.)
- **프로토타입 파일은 크기·경고문에 앞서 구조부터 확인**: 통짜 프로토타입 HTML을 "참고자료"로 오판해 프론트 골격을 방치한 적이 있다(실제론 화면마다 독립 완성 스펙). 다음엔 "색/픽셀은 임시" 같은 경고문의 적용 범위를 넘겨짚지 말고, 큰 프로토타입 파일을 받으면 제일 먼저 화면별 분리 여부(예: iframe/서브페이지 구조)부터 열어 확인.
