# 패턴 — 소프트삭제 = 지우지 말고 숨겨서 복구 가능 (soft-delete-hide-recover)

> 승격: 2026-06-18 (`/retro` 아카이브 채굴). 근거: `archive/llm-wiki/knowledge.md`("아카이브 룸 복구")·`archive/llm-wiki/ideas.md`("소프트삭제 숨기고 복구"). ⚠️ company-internal 일반화.

---

## 결정 (fork) — 무슨 갈림길인가

컨테이너(룸·프로젝트·워크스페이스·채널 등)를 삭제할 때
**`archivedAt` 타임스탬프로 숨기고 복구 가능**하게 할 것인가,
**즉시 물리 삭제(hard delete)**할 것인가,
또는 **별도 휴지통 테이블**로 옮길 것인가.

---

## 계기·증거 — 어느 프로젝트에서 무엇이 실패·통했나

**멀티테넌트 협업 앱(llm-wiki 계열)**: 룸(room) 삭제에 hard delete를 쓰면 실수 복구가 불가능하다는 요구가 있었다.

`archivedAt` 타임스탬프 하나를 추가했다. 단일 권한 계산처([[single-permission-point]])가 이미 `archivedAt IS NOT NULL`을 막고 있어서, 추가 코드 없이 **편집·AI 호출·승격 버튼이 자동으로 숨겨졌다**. 쓰기 경로는 차단되고 읽기 경로만 통과시켜 읽기전용 열람과 소유자 복원이 가능해졌다.

스키마 변경은 컬럼 하나 추가뿐이었고, 별도 테이블이나 데이터 이동 없이 복구 경로가 확보됐다.

---

## 선택지와 트레이드오프

### A. Soft delete (`archivedAt` 타임스탬프)
- **득**: 복구 가능, 스키마 변경 최소(컬럼 하나), 단일 권한 계산처와 결합 시 UI 자동 반응, 감사 이력 보존
- **실**: 모든 쿼리에 `archived IS NULL` 필터 필요(누락 시 archived 항목이 노출됨), 데이터가 DB에 계속 잔존

### B. Hard delete
- **득**: DB 깔끔, 구현 단순, 법적·프라이버시 요건 충족(진짜 지워야 하는 경우)
- **실**: 복구 불가, 실수 한 번에 영구 소실, 운영·UX 위험

### C. 휴지통 테이블 (별도 테이블로 이동)
- **득**: 삭제 의도가 명시적, 원본 테이블 쿼리 단순
- **실**: 스키마 복잡(동기화 유지), 데이터 이동 코드 필요, 대부분의 경우 soft delete보다 과한 구조

## 언제 이대로 · 언제 다르게

**Soft delete를 택할 때**:
- 멀티테넌트 앱의 컨테이너(룸·프로젝트·워크스페이스·채널) 삭제 — 실수 복구 요구가 있는 경우
- 단일 권한 계산처가 이미 있어 `archivedAt` 조건을 자동으로 반영할 수 있는 경우
- 감사 이력·삭제 시점 기록이 필요한 경우

**Hard delete를 택할 때**:
- GDPR·개인정보 법령상 진짜 삭제가 필요한 경우(right to erasure)
- 복구 요구가 없고 데이터 최소화가 중요한 경우
- 단순 로그·임시 데이터 정리

> 핵심 분기: 쓰기 경로는 차단, 읽기 경로만 통과 → 읽기전용 열람 + 소유자 복원 허용.
> 복원 = `archivedAt = NULL` 업데이트만 — 데이터 이동 없음.
> UI 패턴: 사이드바 하단 접이식 '아카이브(N)' 섹션으로 재노출 — 메인 목록 깔끔, 복구 한 클릭.
