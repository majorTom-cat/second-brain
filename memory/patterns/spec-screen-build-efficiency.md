# 패턴 — 시안/기획 1:1 화면을 *품질 타협 없이* 빠르게

> 출처: intra 차량 흐름(2026-06-20). car-new(비쌈) → car-edit·car-detail·회의실(쌈)의 비대칭에서 추출.
> 열린 패턴: "이대로 따라 해라"가 아니라 *왜·언제 그렇게* (lesson-distiller ★).

## 결정(fork) — 진짜 프로젝트의 화면을 어떻게 짓나
- **A 화면마다 처음부터** (증분 발견·매번 재결정) — 첫 화면도 N번째 화면도 똑같이 비쌈.
- **B 첫 화면 = 재사용 키트로, 발견은 앞단 1패스** — 첫 화면은 비싸지만 형제가 분할상환.
- ❌ "단순한 화면은 러프하게" 는 *진짜 프로젝트엔 무의미*(시안/기획 안 따른 산출물 = 폐기물). 효율은 *대충*이 아니라 *재사용*에서.

## 계기 — 무엇이 car-new를 비싸게 했나 (= 다음에 앞당길 것)
1. **증분적 발견**: 시안을 여러 번 나눠 읽음 · 스키마/액션/테스트 결합을 *빌드 중간에* 발견 → thrash.
2. **신규 인프라**: 스키마 컬럼·액션 파서·실시간 가용을 처음부터.
반대로 car-edit가 싼 이유 = **공유 폼 재사용**(한 컴포넌트 파라미터화), car-detail = **확장만**.

## 플레이북 (품질=비협상, 속도는 재사용+앞단발견에서)

### PHASE 1 — 발견을 *전부 앞단에서 1패스* (빌드 전)
1. **시안 통독**(나눠읽기 ❌): 바디 필드 + `<style>`(쓸 수 있는 CSS 클래스) + `<script>`(인터랙션·상태·검증식) + **제외할 프로토타입 비계**(.scrnav 화면흐름·.scntog 시나리오토글·배경 캘린더).
2. **데이터 매핑표**: 시안 필드마다 → *기존 스키마 / 신규 컬럼 / 표시전용*. 필요한 스키마 변경을 **전부 목록화**(중간 발견 금지).
3. **테스트 결합 파악**: 그 화면의 라우트·테스트를 *먼저* grep → 무엇을 갱신할지 + **안정 셀렉터(id 등)로 테스트 호환되게 설계**(폼 바꾸면 그 화면 e2e/interaction 테스트가 깨진다는 걸 알고 시작). DB 불변식 테스트가 서버 제약을 따로 검증하면 e2e는 *클라 UX*만 봐도 됨(중복 회피).
4. **케이스 시드 먼저**: 그 화면의 *상태별*(reserved/returned/active/inactive/answered…) 데모를 빌드 *전에* 시드에 — 만들면서 바로 실상태로 검증. append 로 기존 ID 불변.

### PHASE 2 — 빌드는 *키트 재사용/제작*
5. **스키마 변경 1패스**: DDL(`migrations/*.sql`) + drizzle `schema.ts` 동시 → drop+reset 로 적용(마이그레이션은 테이블 없을 때만 도니 컬럼 추가엔 drop 필요).
6. **공유 컴포넌트 키트**: 같은 패밀리(예약 폼)의 위젯을 **재사용 단위**로 — 리치 폼·asset-pick·시:분 picker·From→To+종일·avail-note·실시간 가용 계산. **첫 화면을 파라미터화**(mode/action/initial/editId/fields)해 형제(수정·다른 자원)가 *조합만*. ← **최대 승수**.

### PHASE 3 — 검증을 *템플릿화*
7. 표준 렌더체크(로그인→goto→위젯·인터랙션·상태 단언) 일회용 스크립트 + 전체 테스트 + 끝에 db:reset(공유DB·로그인 복구). green ≠ 완료 — 렌더로 시안 대조.

## 언제 이대로 / 언제 다르게
- **이대로**: 디자인 시안 + 기획이 정본인 *진짜 프로젝트*. 화면이 "패밀리"(반복 구조)를 이룰 때 키트화 이득 큼.
- **다르게**: 일회성 프로토타입·내부 도구(시안 없음)면 키트 투자 회수 안 될 수 있음 → 그땐 가볍게. (단 "진짜 프로젝트"엔 적용 안 함.)
- **신호**: 비슷한 화면이 2개+ 보이면 *첫 화면을 키트로*. 한 화면뿐이면 인라인.
