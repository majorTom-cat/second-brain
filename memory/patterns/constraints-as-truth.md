## 결정 (fork) — 무슨 갈림길인가

불변식(시간겹침 금지·동시쓰기 금지·익명성 등)을 지킬 때,
**앱 로직으로 검사**할 것인가, **구조적으로 불가능하게** 만들 것인가.

- 앱 검증: 코드에서 `if` 체크·SELECT-후-INSERT 패턴으로 불변식을 확인
- 구조적 강제: DB 제약(EXCLUDE, CHECK, UNIQUE)·단일 라이터·스키마 설계로 위반 자체를 차단

---

## 계기·증거 — 어느 프로젝트에서 무엇이 실패·통했나

**예약 시스템(agora 계열)**: 자원 예약 시 시간겹침 방지를 앱 로직에만 맡기면
SELECT-후-INSERT 사이에 다른 트랜잭션이 끼어들어 이중예약이 발생한다.
`EXCLUDE USING gist (resource_id WITH =, period WITH &&)` 제약을 DB에 걸자
레이스 컨디션이 구조적으로 사라졌다(DB 직렬화 보장).

**지식 워커(llm-wiki 계열)**: 생성 산출물을 여러 프로세스가 동시에 쓰면 충돌이 난다.
git-backed 파일 스토어에 단일 라이터 프로세스만 허용하는 구조로 바꾸자
락·트랜잭션 없이도 동시쓰기 충돌이 구조적으로 제거됐다.

두 프로젝트는 메커니즘은 달랐지만(DB 제약 vs 단일 라이터) 같은 원리를 적용했다:
"앱에서 항상 확인해야 한다"는 주석 대신 애초에 불가능한 구조.

## 선택지와 트레이드오프

### A. 구조적 강제 (DB 제약·단일 라이터·스키마 CHECK·필드 부재)
- **득**: 레이스 컨디션 0, 새 기능이 체크를 빠뜨려도 불변식 유지, "없는 필드는 새지 않는다"
- **실**: DB 전용 기능 종속(이식성↓), 기능 학습 비용, 인프라 변경 시 제약 재설계 필요

### B. 앱 검증 (코드에서 조건 검사)
- **득**: 이식성 높음, 코드 단순, 빠른 프로토타입, DB 기능 미지원 환경에서도 동작
- **실**: SELECT-후-INSERT 레이스, 새 기능에서 체크 누락 위험, "항상 이걸 확인해야 해" 주석이 결국 빠짐

## 언제 이대로 · 언제 다르게

**구조적 강제를 택할 때**:
- 예약·자원선점·동시성처럼 정확성이 핵심이고 레이스 허용치가 0인 도메인
- 익명성·개인정보처럼 필드 부재 자체가 누수 차단인 경우
- 멀티테넌트·ACL에서 권한 누락이 보안 결함인 경우

**앱 검증(또는 다른 방법)을 택할 때**:
- 빠른 프로토타입이나 POC에서 이식성이 우선인 경우
- 그 DB 기능을 사용할 수 없는 환경(경량 SQLite, 레거시 스택)
- 불변식 위반이 치명적이지 않고 사후 수정이 가능한 경우

> 슬로건: "스키마는 표현이 아니라 **정책을 강제**한다." / "없는 필드는 새지 않는다."
