# 패턴 — 단일 권한 계산처 (single-permission-point)

> 승격: 2026-06-18 (`/retro` 아카이브 채굴). 근거: `archive/llm-wiki/knowledge.md`("ACL 4 강제지점·단일 계산처"). ⚠️ company-internal 일반화.

---

## 결정 (fork) — 무슨 갈림길인가

권한 판정 로직을 **단일 계산처 함수 하나**에 집중할 것인가,
**각 강제지점(라우터·서비스·UI·API)마다** 직접 짤 것인가.

- 단일 계산처: `canAct(subject, action, resource)` 형태의 함수 하나를 모든 지점이 호출
- 분산 구현: 각 레이어가 필요에 따라 독자적으로 권한 조건을 작성

---

## 계기·증거 — 어느 프로젝트에서 무엇이 실패·통했나

**위키·멀티테넌트 앱(llm-wiki 계열)**: scope/visibility/역할을 판정하는 함수(`canManageScope`)를
단일 계산처로 만들고, 질의 입력·페이지 로드·인제스트·파일링 등 4개 강제지점이 공용으로 호출했다.

이후 soft-delete된 항목의 복원 기능을 추가했을 때 별도 권한 코드를 추가하지 않아도
편집 버튼이 자동으로 숨겨졌다 — 계산처가 이미 `archivedAt IS NOT NULL`을 `false`로 처리했기 때문.

반대로 권한 체크가 여러 곳에 흩어진 경우, 새 기능 추가 시 한 지점을 빠뜨려 권한 누수가 생기는 사례를 같은 프로젝트 초기에 경험했다.

---

## 선택지와 트레이드오프

### A. 단일 계산처
- **득**: 권한 로직 변경이 한 곳에만 집중, 새 기능이 자동으로 일관성 확보, 테스트 범위 명확
- **실**: 계산처 함수가 비대해질 수 있음(scope/action 경우의 수 증가), 지점별 미세 조정이 어색할 수 있음

### B. 분산 구현
- **득**: 각 지점에서 문맥에 맞게 유연하게 조건 작성 가능, 초기 구현이 단순
- **실**: 누락·불일치 위험, 역할 모델 변경 시 수정 지점을 전부 찾기 어려움, 미묘한 차이 누적

---

## 언제 이대로 · 언제 다르게

**단일 계산처를 택할 때**:
- scope·visibility·역할(role)이 있고 강제지점이 2곳 이상인 멀티테넌트·ACL 앱
- 권한 규칙이 자주 바뀌거나, soft-delete·상태변화 등 리소스 상태가 권한에 영향을 줄 때
- 권한 누락이 보안 결함이 되는 도메인(노출해선 안 되는 데이터)

**분산 구현(또는 단순 인라인)을 택할 때**:
- 권한 판정이 단순하고 강제지점이 딱 한 곳뿐인 경우 (추상화 오버헤드가 더 큰 경우)
- 프로토타입 단계에서 빠르게 검증할 때 (이후 리팩터링 예정)
