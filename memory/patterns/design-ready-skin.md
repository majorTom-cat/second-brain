# 패턴 — Design-ready 스킨: 구조 먼저, 비주얼은 토큰 1패스로 나중에

> 승격: 2026-06-18 (`/retro` 아카이브 채굴). 근거: `archive/agora/ideas.md`("Design-ready 스킨 흡수 키트"),
> `archive/agora/knowledge.md`(노하우 Design-ready). ⚠️ company-internal 일반화.

## 결정 (fork) — 무슨 갈림길인가

디자인 최종안이 늦게 올 때, 세 선택지가 있다:

**① 기다리기** — 비주얼 확정까지 개발 보류
vs **② 임의 구현 후 갈아엎기** — 지금 빠르게 만들고 시안 도착 시 전면 수정
vs **③ 토큰 골격 먼저 + 비주얼은 토큰 1패스로 흡수** (이 패턴)

## 계기·증거 — 어느 프로젝트에서 무엇이 실패·통했나

- **agora CR-001** — 디자인 토큰 단일출처(`:root`) + `[data-theme]` 오버라이드 구조를 먼저 깔았더니,
  최종 시안 도착 시 토큰값 교체 1패스로 전 화면 스킨 완료. JSX 컴포넌트 코드는 거의 불변.
- **같은 프로젝트 이전 시도(②)** — 임의 색·치수로 먼저 구현했다가 시안 도착 후 전 화면을 수작업으로
  갈아엎는 낭비가 반복. 기획↔디자인 분리·러프 반복 프로젝트에서 이 패턴이 특히 두드러짐.

## 선택지와 트레이드오프

| | ① 기다리기 | ② 임의 구현 후 갈아엎기 | ③ 토큰 골격 먼저 (이 패턴) |
|---|---|---|---|
| **진행 속도** | 막힘 | 당장 빠름 | 초기 셋업 후 진행 |
| **시안 흡수 비용** | 없음(아직 안 만듦) | 大 — 전 화면 수작업 수정 | 小 — 토큰값 교체 1패스 |
| **롤백 안전성** | 해당 없음 | 낮음 | 높음 (`data-theme` 제거로 즉시 롤백) |
| **초기 규율 비용** | 없음 | 없음 | 있음 — 하드코딩 0 강제 필요 |
| **적합 상황** | 일정 여유 있고 디자인 곧 확정 | 일회성 throwaway | 디자인 늦게 확정·러프 반복·브랜드 미정 |

## 언제 이대로 · 언제 다르게

- 이대로(③ **토큰 골격**) 할 신호:
  - 디자이너 시안이 개발보다 늦게 확정되는 프로젝트
  - 러프부터 만들어 HANDBACK 루프가 예상될 때
  - 브랜드 색·타이포·여백이 미확정인 채로 개발을 시작해야 할 때
  - 기존 프로젝트에 전면 리디자인이 들어올 때
  - 다중 테마·화이트라벨 요구가 있을 때
- 다르게 갈 신호:
  - 디자인이 **이미 확정**됐다면 → 바로 구현, 토큰 추상 레이어 불필요(과투자)
  - **일회성 throwaway** 프로토타입 → 토큰 규율 비용이 이득보다 큼
  - 디자인 시스템이 외부(예: MUI·Ant Design)로 고정됐다면 → 토큰 대신 라이브러리 테마 API 사용

## 레일 적용 (빌드는 backlog)

- `/develop` 러프(`rough`) 단계: `REQ-SCR-NNN` 구현 시 컴포넌트에 토큰 골격만 깔고 임시값 사용
- `/develop` 풀(`full`) 단계 진입 조건에 "디자인 토큰 매핑시트 완성" 추가
- `spec-author` 스킬: 화면 REQ 작성 시 "토큰 출처 명시" 필드 포함 권고
- HANDBACK 게이트에서 이 패턴 체크리스트(토큰 단일 출처 · 운영색 DB 분리 · 매핑시트 존재) 검증

### 토큰 골격 주 선택 시 기본 구현 (검증된 방식)

**① 디자인 토큰 단일 출처**

- `globals.css :root`에 모든 색·치수·간격 토큰 선언
- 컴포넌트는 `var(--token)`만 참조 — 색·치수 하드코딩 0
- 러프 단계에서 임시값으로 채워도 구조는 완성: 시안 도착 시 `:root` 값만 교체
- 다르게: 컴포넌트 라이브러리가 자체 CSS vars를 쓴다면 해당 라이브러리 토큰 시스템에 맞춤

**② 운영 데이터 색은 DB 마스터 필드로 분리**

- 부서 색·자산 분류 색 등 운영 중 바뀌는 색상 → 디자인 토큰이 아니라 DB 레코드 필드
- 이유: 토큰은 브랜드 정체성(느리게 변함), 운영 색은 데이터(수시로 변함) — 섞으면 둘 다 관리 불가
- 다르게: 색이 정말 고정 브랜드라면 토큰으로 관리 가능

**③ `[data-theme="vN"]` 스킨 레이어로 안전하게 전환**

```css
/* 러프 — 임시 토큰 */
:root { --color-primary: #888; --radius-card: 8px; }

/* 시안 도착 후 — 먼저 오버라이드로 비교 */
[data-theme="v2"] { --color-primary: #0050FF; --radius-card: 12px; }
```

- 새 디자인을 오버라이드로 먼저 입혀 기존 화면과 **나란히 비교** 후 `:root`로 승격
- 문제 발견 시 `data-theme` 속성만 제거하면 즉시 롤백
- 다르게: 테마 전환이 필요 없는 단일 배포라면 오버라이드 없이 `:root` 직접 교체도 무방

**④ "디자인 이미지 → 토큰명" 빈 매핑시트를 docs에 미리 배치**

```
docs/design-token-map.md
| 디자인 레이어명 | 토큰명 | 현재값(임시) | 확정값 |
|----------------|--------|-------------|--------|
| Primary/500    | --color-primary | #888 | (미정) |
```

- 시안 도착 즉시 디자이너·개발자가 함께 채움 → 토큰값 교체 1패스로 전 화면 일괄 스킨
- JSX/컴포넌트 코드는 거의 불변

## ★ 공통 주의 (함정)

- **하드코딩 1개가 패턴을 깨뜨린다**: 컴포넌트 한 곳이라도 색을 직접 넣으면 1패스 흡수가 불완전해짐. 코드 리뷰에서 `#[0-9a-fA-F]{3,6}` 리터럴 탐지 권장.
- **운영 색을 토큰에 섞으면 릴리즈 없이 못 바꾼다**: DB 필드 vs 토큰 경계를 초기에 명확히.
- **매핑시트를 나중에 만들면 시안 도착 후 혼란**: 러프 시작 시점에 빈 시트를 만들어두는 것이 핵심.
