### 잘 작동한 것 (다음에도 기본값)

- **발산 3안이 "대립"이 아니라 "단계"로 수렴** — A(최단)·B(정밀)·C(패키징)를 병렬로 받았더니 셋 다
  "A 먼저, B·C는 승격 경로"를 스스로 권장. 심사가 고르기가 아니라 **로드맵 합성**이 됨. 언제 같게: 방향들이
  직교(속도/품질/포장)일 때. 언제 다르게: 진짜 배타적 선택(스택 A vs B)이면 승자 골라야.
- **배포 결정 즉시 라이선스 전수 감사** — "밴드 배포" 말이 나온 그 턴에 감사를 돌려 ❌ 3건(모델 가중치)을
  코드 작성 전에 발견 → 이중 모델 전략으로 설계에 흡수. 배포·공개가 스코프에 들어오는 순간이 감사 적기.
- **acceptance 를 합성 픽스처로** — "타브 정확도"처럼 주관적인 요구를 "정답을 아는 합성 베이스라인(MIDI→렌더)에서
  ≥80%"로 falsifiable 하게. 도메인 품질 요구엔 이 패턴이 재사용 가치.
- **스파이크 실패 = 강등/중단 게이트를 스펙에 명문화**(SP-1 실패→중단, SP-4 실패→TAB P2 강등) — "실측이
  나쁘면 어떻게 되나"를 미리 적어 헛개발과 매몰비용 논쟁을 차단.
- **사용자 게이트 반복(rev1→7)이 스펙을 키운 것은 비용이 아니라 설계의 목적대로 작동한 것** — 코드 없이
  REQ 28→47. 같은 변경을 개발 후에 했으면 재작업 몇 배.

### 실패·마찰 (레일이 배울 것)

1. **시안 v1을 벤치마크 없이 만듦** — 스펙만 보고 그림 → 사용자가 "기존 제품 참고했어?"로 반려 → UI 벤치마크
   3방향 후 v2. **시안 제작 전 "실제 제품 UI 벤치마크" 스텝이 레일에 없다**(spec-author 는 문서만 다룸).
2. **도메인 표준 산출물(악보)을 손그림으로 2회** — v3 반려("일반적이지 않다")→v3.1 재손질→또 부족→v3.2 에서야
   실제 렌더러(alphaTab) 내장으로 근본 해결. 교훈 자체는 auto-memory 로 승격했지만, **레일 관점: critic/false-done
   에 "도메인 표준 대조" 항목이 없어서 내 QA(렌더 됨·에러 0)가 통과시켰다** — 검사 항목 갭.
3. **위임 산출물이 프로젝트 원칙 위반**(S/M 약어 — 브리프의 "쉬운 말" 위반) — 원칙이 브리프에 있어도 위임
   프롬프트에 안 실리면 없는 것. 레일의 R4a(bulk→Sonnet) 라우팅 계약에 **"주입 세트" 규칙이 없다**.
4. **동시 서브에이전트 작업 중 `git add -A`** — 에이전트가 편집 중이던 파일이 무관한 스펙 커밋에 쓸려 들어감
   (내용 무손상·귀속만 오염). [[shared-repo-db-sessions-not-isolated]] 가 서브에이전트에도 적용됨을 실증.
5. **비목표 뒤집기(악보 생성)가 세션 중 두 번** — 유저의 정당한 방향 전환이지만, 브리프 비목표를 뒤집을 땐
   기록 규율([[intentional-design-divergence-needs-adr]])이 없었으면 다음 세션이 "스펙과 다름"으로 되돌렸을 것.
   00-brief 에 취소선+이유로 기록한 방식이 유효했음 — 템플릿에 관례로 명시할 가치.
