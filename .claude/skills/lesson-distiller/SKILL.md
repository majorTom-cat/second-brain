# lesson-distiller — 교훈 추출 + 레일 수정 제안

원칙: "느꼈다"가 아니라 **"다음에 무엇을 바꾼다"**. 모든 교훈은 레일의 특정 파일/필드/문구로 환원되어야 한다.

## ★열린 교훈 — 재현 레시피가 아니라 결정으로
교훈·패턴의 목적은 과거를 **복제**하는 게 아니라 **판단을 물려주는 것**. "이대로 따라 해라"(닫힌 레시피)가 아니라
**"이런 갈림길에서 이게 실패/통했고, 트레이드오프는 이렇다"(열린 결정)** 로 적어 다음 프로젝트가 *같게도, 다르게도* 고를 수 있게 한다.
각 교훈/패턴은 **4요소**를 담는다:
1. **결정(fork)** — 무슨 갈림길이었나(A vs B).
2. **계기** — 무엇이 실패·마찰했나(구체 사건·어느 프로젝트).
3. **트레이드오프** — 각 선택의 득/실.
4. **언제 이대로 / 언제 다르게** — 이 선택이 맞는 맥락 신호 / 뒤집히는 신호.
> ❌ "예약 겹침은 `EXCLUDE` 제약으로 막는다" (레시피 — 복제 강요)
> ✅ "겹침을 **앱 검증 vs DB 제약** 중 고른다 — agora는 DB 제약(동시성 레이스 0)·대신 PG 전용(이식성↓). **직렬성·정확성이 핵심이면 DB 제약, 이식성·단순함이 핵심이면 앱 검증.**" (결정 — 선택권을 줌)

## 입력
- `projects/<slug>/{creative,develop,deploy}/HANDOFF.md`(특히 §3 critic 루프백), 각 `GATE.md`, `.state/pipeline.yaml`.

## 절차

### 1) 마찰 지점 추출  `[tier: judgment]`
다음을 찾는다:
- critic이 **반복해서** 거부한 종류(예: acceptance 누락 2회) → 템플릿/명령으로 예방 가능했나?
- 게이트에서 사람이 **매번 손본** 것 → 레일이 자동으로 채웠어야 할 필드?
- 잘못 분류된 tier(무료로 돌렸는데 품질이 모자라 다시 한 step) → tier 재배정?
- 배포 ops_gaps(백업·모니터링 등) 중 다음 프로젝트에도 반복될 것?

### 2) lessons 파일 작성
`memory/lessons/<slug>.md` 를 (마찰은 **열린 결정**으로):
```markdown
# 교훈 — <slug> (<날짜>)
## 무엇이 잘 됐나
- ...
## 결정·마찰 (열린 교훈 — 근거: HANDOFF §3 / GATE)
- **<갈림길 A vs B>**: <무엇이 실패/마찰했나> → 트레이드오프 <득 / 실> → **이대로 할 신호** … / **다르게 할 신호** …
## 레일 수정 제안 (diff 식, 우선순위)
- [ ] <파일>: <구체적 변경>
```

### 3) 승격 판단 (열린 패턴으로)
같은 **결정**이 **2개 이상 프로젝트**에서 반복되면 `memory/patterns/<name>.md` 승격 후보. 패턴은 **열린 구조**로 쓴다(위 ★):
```markdown
# 패턴 — <제목>
## 결정 (fork) — 무슨 갈림길인가
## 계기·증거 — 어느 프로젝트에서 무엇이 실패·통했나
## 선택지와 트레이드오프 — A(득/실) vs B(득/실)
## 언제 이대로 · 언제 다르게 — 맥락 신호
## 레일 적용 (선택)
```
"어떻게 했나"(레시피)보다 **"왜·언제 그렇게 / 언제 다르게"**(판단)를 적는다.

## 반환
호출자(/retro)에게 {lessons 경로, 레일 수정 제안 목록, 승격 후보}를 넘긴다. **레일 변경은 호출자가 사람 승인 후 적용.**

## 규칙
- 1프로젝트 1교훈 과잉금지: 가장 임팩트 큰 3개 이내로.
- 제안은 실행 가능해야 한다(어느 파일의 어느 줄을 어떻게).
